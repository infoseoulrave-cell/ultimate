# 우리만의 프로그램 제작: 갖춘 것 vs 빠진 것

## ✅ 갖춘 것 (이미 활용 가능)

| 항목 | 문서 | 활용 방법 |
|------|------|-----------|
| **설계 철학** | NEXUS-CSA.md | 의사결정·평가·커뮤니케이션 원칙. 기능 스펙 작성 시 기준. |
| **에이전트 레이어** | AGENT-DESIGN.md | 제어 / 지능 / 페르소나 3단 구조. 모듈 나누기·인터페이스 설계에 사용. |
| **openclaw 구조** | OPENCLAW-STRUCTURE.md | 연동 포인트(Gateway WS, CLI, plugin-sdk), 확장 방식(extensions/skills) 참고. |
| **Cursor 규칙** | .cursor/rules/nexus-ultimate.mdc | 이 리포에서 작업할 때 NEXUS 원칙 자동 적용. |

→ **결론: 이 정보만으로 “무엇을 만들지”와 “어디에 붙일지”는 정해진 상태.**  
→ **“어떤 스택으로, 어떤 순서로 구현할지”는 아래 보완이 필요.**

## ❌ 빠진 것 (구현 전에 채우면 좋은 것)

### 1. 아키텍처 선택

| 질문 | 선택지 예시 | 결정 시 영향 |
|------|-------------|--------------|
| **ultimate와 openclaw 관계** | (A) openclaw **플러그인**(extension/skill) (B) **별도 프로세스**가 Gateway/CLI 호출 | (A) openclaw 생태계 안, (B) 독립 서비스·다른 UI 가능 |
| **진입점** | CLI 전용 / 로컬 웹 서버 / TUI / 데스크톱 앱 | 프로젝트 뼈대(진입 스크립트, 서버 유무) |
| **언어·런타임** | Node(TS) / Python / 기타 | 패키지 구조, openclaw와 같은 Node로 갈지 여부 |

→ **지금 없음**: “ultimate는 openclaw의 ○○ 로 동작한다” 같은 한 줄 정의.

---

### 2. 연동 스펙 (제어 레이어)

| 항목 | 현재 | 보완 시 |
|------|------|---------|
| **Gateway 연동** | “WS로 제어” 수준 | 실제 사용할 WS 메서드 목록(`sessions.*`, `node.invoke` 등), 인증·포트 가정 |
| **CLI 호출** | `openclaw agent …` 언급 | 서브프로세스로 쓸 명령 목록, 입출력 포맷(JSON 등) |
| **openclaw 설정** | `~/.openclaw/openclaw.json` 경로만 문서화 | ultimate가 읽어야 할 최소 설정 키(예: gateway.port, agents.defaults.workspace) |

→ **지금 없음**: “ultimate ↔ openclaw” 프로토콜/API 한 페이지 스펙.

---

### 3. API 두뇌 (지능 레이어)

| 항목 | 현재 | 보완 시 |
|------|------|---------|
| **LLM/에이전트 API** | “외부·내부 API 활용” 수준 | 사용할 서비스(OpenAI/Anthropic/로컬 등), 인증 방식, 모델 고정 여부 |
| **도구 정의** | “도구/함수 호출” 수준 | 최소 도구 목록(파일 읽기, openclaw 명령 래핑, 브라우저 등) + 스키마(이름, 인자, 설명) |
| **컨텍스트** | “화면·파일·에디터 상태” 언급 | 실제 수집 방식(예: 워크스페이스 경로, 현재 디렉터리, 환경 변수) |
| **세션/대화 상태** | 미정의 | 턴 저장 여부, 히스토리 길이, 저장소(메모리/파일/DB) |

→ **지금 없음**: “어떤 API를 어떻게 호출하고, 어떤 도구를 갖출지” 명시.

---

### 4. 페르소나 구현

| 항목 | 현재 | 보완 시 |
|------|------|---------|
| **따뜻한 톤** | “공감, 인사, 격려” 수준 | 시스템 프롬프트 초안, 금지/권장 문구, 길이·스타일 가이드 |
| **NEXUS와 분리** | “로직 vs 말투 분리” 원칙만 | 응답 파이프라인(내부 판단 → 사용자 문장 변환) 단계 정의 |
| **다국어** | 미정의 | 기본 언어(한/영), 필요 시 확장 방식 |

→ **지금 없음**: 재현 가능한 “따뜻한 톤”용 프롬프트/규칙 1세트.

---

### 5. 안전·권한·운영

| 항목 | 현재 | 보완 시 |
|------|------|---------|
| **실행 범위** | “권한·샌드박스 정책” 언급 | 허용 디렉터리, 금지 명령, 네트워크 제한 |
| **되돌리기** | “undo 정책” 언급 | 어떤 액션에 undo를 붙일지, 로그/스냅샷 여부 |
| **비밀/키** | 미정의 | API 키·토큰 보관 위치(env/파일), 리포에 올리지 않을 것 목록 |
| **로깅·KPI** | “피드백 루프에 반영” 수준 | 로그 포맷, 저장 위치, NEXUS용 최소 지표(호출 횟수, 에러율, 작업 완료 여부 등) |

→ **지금 없음**: “기본으로 허용/금지하는 것”과 “측정할 것” 목록.

---

### 6. 프로젝트 뼈대

| 항목 | 현재 | 보완 시 |
|------|------|---------|
| **코드** | 없음 | 진입점(CLI 또는 서버), 패키지 매니저, 디렉터리 구조(src/, config 등) |
| **설정** | NEXUS/에이전트 설계만 | ultimate 전용 설정 파일 스키마(선택 항목·필수 항목) |
| **의존성** | 미정의 | 최소 패키지(예: openclaw 연동용 ws, LLM 클라이언트, 설정 파서) |

→ **지금 없음**: `npm/pnpm init` 후 “첫 동작하는 한 사이클”까지의 폴더/파일 계획.

## 🗺 제안 로드맵 (빠진 것 채우는 순서)

1. **아키텍처 결정**  
   - ultimate를 “openclaw 플러그인” vs “독립 프로세스” 중 하나로 고정.  
   - 진입점(CLI vs 서버 vs 앱) 결정.

2. **연동 스펙 1페이지**  
   - openclaw Gateway WS에서 쓸 메서드 + (선택) CLI 호출 규약.  
   - `docs/`에 `OPENCLAW-INTEGRATION.md` 같은 문서로 정리.

3. **API·도구 목록**  
   - 사용할 LLM 1개 + 최소 도구 3~5개(예: openclaw 래퍼, 파일 읽기, 현재 컨텍스트).  
   - `docs/` 또는 설계서에 “API 두뇌 명세” 섹션 추가.

4. **페르소나 초안**  
   - 시스템 프롬프트 1개 + “따뜻한 톤” 규칙 몇 줄.  
   - `docs/PERSONA.md` 또는 AGENT-DESIGN에 하위 섹션.

5. **프로젝트 뼈대 + 프로토타입**  
   - 저장소에 진입점·설정·의존성 추가.  
   - “한 번 사용자 입력 → openclaw 또는 로컬 1액션 → 따뜻한 응답” 한 사이클 구현.

6. **안전·로깅**  
   - 허용/금지 목록, API 키 보관 방식, 최소 KPI·로그 포맷.

---

## 요약

- **이미 있는 정보만으로도** 방향·레이어·연동 후보는 정해져 있어서, “우리만의 프로그램” 설계와 openclaw 활용은 **충분히 가능**하다.
- **빠진 것**은 주로 “구체적 선택·스펙·한 페이지 명세”다.  
  - 아키텍처(플러그인 vs 독립, 진입점),  
  - openclaw 연동 스펙,  
  - API·도구·페르소나·안전·로깅의 구체화,  
  - 실제 코드 뼈대와 첫 프로토타입.
- 위 **로드맵 순서**대로 하나씩 문서/코드로 채우면, 설계한 내용을 그대로 구현에 반영할 수 있다.
