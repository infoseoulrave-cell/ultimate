# 서브에이전트 회의: Ultimate가 더 똑똑해지려면?

**참석**: 아키텍트(Arch), 메모리(Mem), 도구·추론(Tool)  
**목적**: Ultimate 에이전트를 더 똑똑하게 만들기 위한 방안 논의

---

## 1. 자기소개

**Arch (아키텍트)**  
저는 구조와 확장성 담당입니다. “똑똑해진다”는 건 단일 모델이 아니라 **시스템 전체**가 더 나은 결정을 내리는 걸로 봅니다. 데이터 흐름, 레이어 분리, 피드백 루프가 명확해야 진화할 수 있습니다.

**Mem (메모리)**  
저는 기억·학습 담당입니다. 똑똑해지려면 **과거를 잘 쓰는 것**이 중요하다고 봅니다. 지금은 JSONL에 요약만 쌓는데, 검색 품질·요약 품질·장기 기억 구조를 올려야 합니다.

**Tool (도구·추론)**  
저는 도구와 추론 담당입니다. “똑똑함”은 **언제 어떤 도구를 쓸지**, **몇 단계로 나눌지**를 잘 결정하는 쪽에 가깝다고 봅니다. 도구 스키마·체인·검증이 있으면 실수가 줄어듭니다.

---

## 2. 회의 내용

### Q: 더 똑똑해지려면 무엇이 가장 시급한가?

**Arch**  
우선 **“똑똑함”을 측정할 수 있어야** 합니다. 지금은 호출 횟수·도구 호출 수만 있는데, “작업 성공 여부”, “사용자 만족 플래그”, “목표 달성률” 같은 지표가 없으면 개선 방향을 못 정합니다. 그래서 **최소 하나의 “성공/실패” 시그널**을 로그에 넣고, 그걸 기준으로 프롬프트·도구 순서를 바꾸는 게 시급합니다.

**Mem**  
동의합니다. 그다음으로 **지식 저장소 품질**이 중요합니다. 지금 `save_knowledge`는 요약 텍스트만 넣고, 검색은 키워드 매칭이라 “의미”로 찾기 어렵습니다. 더 똑똑해지려면 (1) **임베딩**으로 저장하고 유사도 검색하거나, (2) 요약을 **구조화**(제목·핵심 문장·출처·태그)해서 넣거나, (3) **재활용 빈도**를 기록해 자주 쓰는 지식을 우선 보여주는 식으로 가는 게 좋습니다. 임베딩이 없어도 “최근 N개 + 키워드”를 개선하는 것만으로도 도움이 됩니다.

**Tool**  
저는 **도구 사용 전략**이 시급하다고 봅니다. 지금은 LLM이 한 번에 “fetch_url 하고 save_knowledge 해” 식으로 나가는데, 복잡한 질문이면 **목표 분해 → 단계별 실행 → 중간 검증**이 필요합니다. 그래서 (1) **플랜 단계**를 넣어서 “먼저 A URL 조회, 그다음 요약 저장, 그다음 read_knowledge로 확인” 같은 계획을 한 번 세우고, (2) 각 단계 결과를 다음 입력에 넣거나, (3) “이 단계 성공/실패”를 명시적으로 체크하는 작은 규칙을 두면 실수가 줄어듭니다. 서브에이전트 3명을 쓰는 건 아니고, **한 에이전트가 “계획 → 실행 → 검증” 루프**를 도구로 할 수 있게 하는 게 좋습니다.

---

### Q: 우선순위를 정한다면?

**Arch**  
1순위: **성공/실패 시그널 + 로그**. 2순위: **계획 단계**(Tool 말한 것). 3순위: 지식 검색 개선(Mem).

**Mem**  
1순위: **지식 검색 품질**(키워드 확장이든 임베딩이든). 2순위: 성공/실패 로그. 3순위: 계획 단계.

**Tool**  
1순위: **계획·단계 실행**(플랜 도구 또는 시스템 프롬프트에 “단계로 나눠라” 명시). 2순위: 도구 결과 **검증**(예: fetch_url 후 “내용 있음/없음” 체크). 3순위: 지식 검색 개선.

---

### Q: 공통으로 합의할 수 있는 “다음 3가지”는?

**Arch**  
제안: (1) 호출 끝에 **작업 성공/실패/부분성공** 플래그를 로그에 남긴다. (2) 시스템 프롬프트에 **“복잡한 작업은 단계를 나눠서 실행하라”** 한 줄을 넣는다. (3) 지식 저장 시 **title + summary + url + at** 말고 **tags(키워드 3~5개)** 필드를 추가해, read_knowledge 검색 시 태그도 매칭한다.

**Mem**  
(1)(2) 동의. (3)은 제가 말한 “구조화”와 같은 방향입니다. tags 추가하고, read_knowledge가 **최근순 + 키워드(요약+태그)** 로 필터하도록 하면 됩니다.

**Tool**  
(1)(2)(3) 모두 동의. 추가로 (4) **도구 호출 실패 시** 한 번 재시도하거나, “실패 원인”을 다음 메시지에 넣어서 LLM이 대안을 고르게 하는 건 나중에 넣어도 좋겠습니다.

## 3. 회의 결론 (합의 사항)

| 순서 | 내용 | 담당 관점 |
|------|------|-----------|
| 1 | **성공/실패 시그널** — 매 호출/세션 끝에 “작업 성공 / 부분 성공 / 실패”를 로그에 기록. 나중에 KPI·피드백 루프에 사용. | Arch |
| 2 | **단계적 실행 유도** — 시스템 프롬프트에 “복잡한 작업은 목표를 단계로 나누고, 한 단계씩 도구를 사용한 뒤 결과를 확인하라” 문구 추가. | Tool |
| 3 | **지식 구조화** — save_knowledge에 **tags**(키워드 3~5개) 필드 추가. read_knowledge 검색 시 title/summary/url뿐 아니라 tags도 매칭. | Mem |
| 4 | (선택) 도구 실패 시 원인을 컨텍스트에 포함해 LLM이 대안 선택 가능하게 함. | Tool |
