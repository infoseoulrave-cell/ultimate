## 토론 기록

**H (헤드)**  
지금 Ultimate는 로컬 CLI 에이전트고, NEXUS 페르소나·웹 조회·지식 학습·OpenClaw 연동·이중 정체성 진화까지 들어가 있다. 오늘은 “현재 어떻게 보는지”와 “뭘 먼저 할지”를 팀으로 나눠서 말해 보자. 한 명씩 짧게.

---

**A (아키텍트)**  
구조는 아직 플랫하다. UI / Agent Core / Tool Bus / Memory 4층으로 안 가고, entry–brain–tools–log 한 줄로 가니까 확장하면 붙이기 식이 될 가능성이 크다. 지금 단계에선 괜찮지만, “계획–실행–관찰”을 명시하는 Agent Core 한 층과, 도구를 명시적으로 등록하는 Tool Bus를 미리 인터페이스만 잡아두면 나중에 브라우저·데스크톱 제어 넣을 때 편할 것 같다.

**S (보안·권한)**  
권한이 제품 중심이 아니다. 지금은 read_file allowlist, fetch_url 차단 정도뿐이고, audit은 호출 로그 수준이다. 위험 명령 승인·dry-run·kill switch·전액션 audit이 없어서, “로컬에서 막 돌린다”는 신뢰를 주려면 권한 레이어를 설계해서 도입하는 게 좋다. COMPARISON 문서에 나온 “다른 에이전트”처럼, 허용 경로·승인 플로우·audit 로그를 먼저 정의하는 걸 제안한다.

**U (UX)**  
채팅은 TUI로 되어 있어서 “로컬 프로그램” 느낌은 난다. 다만 첫 실행 시 API 키 없으면 에러만 나오고, `evolve`나 `logs` 같은 부가 명령은 README를 봐야 알 수 있다. “한 번 켜면 뭘 할 수 있는지” 한 줄 안내나, `ultimate`만 쳤을 때 최소 사용법을 한 번 찍어주면 진입 장벽이 낮아질 것 같다.

**M (메모리)**  
지식은 JSONL + 키워드/태그 검색이라 단순하다. 항목이 많아지면 “의미” 검색이 어렵다. 단기에는 태그·요약 품질만 잘 쌓아도 되고, 중기에는 SQLite + 벡터(또는 임베딩 검색) 한 단계 도입을 검토할 만하다. 작업 이력·프로젝트 컨텍스트는 아직 없으니, “최근 대화/작업”을 메모리 쪽에 넣는 것도 후보다.

**T (도구)**  
파일은 읽기만 있고 쓰기·터미널 직접 실행은 OpenClaw 경유다. 1차 범위를 “파일/터미널/브라우저 자동화”로 고정한다면, 터미널 실행·파일 쓰기(allowlist 내)·브라우저 스크립트/스냅샷을 우리 쪽 도구로 하나씩 추가하는 게 좋다. 도구 등록을 “툴 버스”처럼 명시적으로 두면, 나중에 플러그인·외부 스킬 붙이기 쉬워진다.

**O (OpenClaw 연동)**  
지금은 run_openclaw 한 도구로 충분하다. OpenClaw 쪽 채널·스킬을 우리가 다시 만들 필요는 없고, “우리 두뇌 + 페르소나 + 일부 전용 도구”만 유지하면 된다. 다만 OpenClaw 스키마/버전이 바뀌면 CLI 호출 방식이 깨질 수 있으니, 연동 스펙을 한 페이지로 정리해두고 필요 시 래퍼만 갈아끼우는 걸 제안한다.

**E (진화)**  
NEXUS/OBSERVER 이중 정체성 + `evolve` 회의는 이미 들어가 있어서 “자기 회귀” 구조는 갖춰졌다. 다만 회의가 수동 실행이라, “N회 대화 후 자동 evolve”나 “스케줄(예: 매일 한 번)” 옵션을 두면 진화가 더 연속적으로 일어날 것 같다. evolution-patch가 너무 길어지면 토크 낭비이니, “최근 1회분 합의만” 유지하는 옵션도 있으면 좋겠다.

**P (페르소나)**  
NEXUS 원칙과 따뜻한 톤이 시스템 프롬프트에 잘 묶여 있다. evolution-patch가 그 위에 붙는 구조라, 회의에서 “말투/규칙”을 바꾸면 다음 대화부터 반영되는 건 잘 맞다. 다만 패치가 NEXUS 원칙과 충돌하지 않도록, “합의는 원칙 위반·권한 완화 금지”를 회의 프롬프트에 한 줄 더 넣어두면 안전하다.

**L (모델)**  
현재는 단일 클라우드 API다. 로컬(Ollama/llama.cpp) 기본 + 고난도만 클라우드로 가려면, “모델 인터페이스”를 추상화해서 호출부가 provider를 바꿀 수 있게 해야 한다. 우선순위는 높지 않지만, 로컬 우선 정책으로 갈 때를 대비해 brain 쪽에서 model 호출만 인터페이스로 빼두는 건 부담이 작다.

**D (문서·온보딩)**  
docs는 NEXUS·설계·아키텍처·진화·비교까지 잘 쌓여 있다. 반대로 “처음 쓰는 사람”용 1페이지(설치 → API 키 → 첫 채팅 → evolve 한 번)가 있으면 좋다. README에 실행 방법은 있으니, “Quick start” 절을 더 짧게 만들고, `ultimate` 인자 없이 실행했을 때 그 절을 인용하는 메시지를 띄우는 것만 해도 된다.

---

**H (헤드)**  
한 바퀴 돌았다. 공통으로 나온 건 세 가지 정도로 보인다.  
(1) **권한·audit** — 제품 수준으로 설계해서 도입.  
(2) **도구 확장** — 파일 쓰기·터미널 직접·브라우저를 1차 범위로 잡고, 도구 등록 인터페이스(Tool Bus 느낌) 정리.  
(3) **온보딩·첫인상** — `ultimate` 단독 실행 시 한 줄 안내, Quick start 1페이지.  
진화 쪽은 이미 구현돼 있으니 “자동/스케줄 + 패치 길이 제한”만 옵션으로 두면 될 것 같고, 메모리·모델은 2차로 가도 된다.  
이걸로 “다음 액션”을 세 개로 고정해도 될까?

## 2차 토론 — 외부 의견 반영

**안건**: 정적 분석 기준 피드백(장점·단점·리스크·필수 3가지)을 팀이 검토하고 대응 방향을 정한다.

### 피드백 요약 (입력)

**장점**
- 구조 분리 명확: entry / brain / persona / tool / evolution.
- 도구 확장 포인트 깔끔 (tools/index.js).
- 로그·KPI 기본 골격 있음 (log.js, entry 호출 로그).
- 이중 정체성 회귀 루프가 실제 구현됨 (evolution.js, DUAL-IDENTITY-EVOLUTION.md).

**단점·리스크**
- 진화 패치가 **무검증**으로 시스템 프롬프트에 주입 → 장기적으로 **프롬프트 오염/드리프트** 위험.
- **run_openclaw**에 승인·타임아웃·샌드박스 없음 → 멈춤·오남용 리스크.
- **fetch_url**: 보안 필터 부분적(사설 대역 일부만), 큰 응답을 전부 읽어서 **메모리 리스크**.
- **read_file** + 도구 로그 조합으로 **민감한 파일 내용이 로그에 남을 수 있음**.
- 지식 저장은 JSONL·키워드 중심이라 **장기 학습 품질/확장성** 제한.
- **테스트 코드 없음** → 회귀 방지 약함.

**총평·필수 3가지**  
설계 철학과 구현 연결은 잘 되어 있고 “빠르게 진화 가능한 기반”은 맞다. 다만 고자유도 + 스스로 똑똑해지는 수준으로 가려면 다음이 **필수**:
1. **진화 게이트** — 검증/점수 통과 시에만 patch 적용.
2. **툴 권한 체계** — 승인·타임아웃·차단 규칙.
3. **회귀 테스트** — 성공률/안전성 자동 체크.

---

### 팀 반응

**H (헤드)**  
장점 쪽은 우리 1차 결론이랑 맞다. 단점·필수 3가지는 그대로 받아서, 각 담당이 반응하고 “우리 결론”을 보강하자.

**A (아키텍트)**  
구조 분리·도구 확장 포인트 인정받은 건 좋다. 필수 3가지는 구조와 다 맞다. 진화 게이트는 evolution 레이어 앞에 “검증 단계” 하나 두면 되고, 툴 권한은 Tool Bus(또는 runTool 진입점)에서 통과시켜야 하니까 아키텍처에 명시하는 게 맞다. 회귀 테스트는 레포에 테스트 골격을 넣고, “도구 호출·진화 패치 적용·권한 거부” 시나리오를 점점 채우면 된다.

**S (보안·권한)**  
run_openclaw 승인/타임아웃/샌드박스, fetch_url 메모리·필터, read_file→로그 유출, 이 세 가지 다 내 담당이다. **툴 권한 체계**를 1순위로 잡자. (1) run_openclaw: 최대 실행 시간 제한·(선택) 사용자 승인 플래그. (2) fetch_url: 스트리밍 또는 크기 상한 후 잘라내기, SSRF 필터 보강(예: RFC 1918 전부). (3) 도구 로그: **파일 내용·본문은 기록하지 않기** — “read_file 경로·성공/실패”만 audit. 민감 정보는 로그에 안 남긴다.

**E (진화)**  
**진화 게이트** 동의한다. 지금은 회의 출력을 그대로 evolution-patch에 넣어서 프롬프트에 붙이는데, 그렇게 하면 악의적이거나 어긋난 합의가 들어갈 수 있다. “게이트”는 (1) 합의 문단이 NEXUS 원칙·금지 규칙과 충돌하지 않는지 체크(키워드/규칙 목록), (2) 또는 별도 LLM 호출로 “이 패치를 적용해도 되는지” 예/아니오 + 이유 한 줄, (3) 통과 시에만 evolution-patch.md 갱신. 점수(스코어)는 2단계에서 “적용 권장 점수”로 두면 된다.

**P (페르소나)**  
프롬프트 오염/드리프트 얘기 맞다. 패치가 누적되면 원래 SYSTEM_PROMPT가 묻을 수 있으니, (1) 패치 최대 줄/글자 수 제한(이미 1차에서 논의), (2) **패치 적용 전 검증(진화 게이트)**이 있으면 드리프트를 줄일 수 있다. 회의 프롬프트에 “원칙 위반·권한 완화 금지”를 넣는 건 1차 결론이었고, 2차에서는 “게이트 통과 시에만 반영”까지 가자.

**T (도구)**  
run_openclaw는 내 쪽 구현이다. 타임아웃은 spawn 쪽에 AbortSignal·max 실행 시간 넣으면 되고, 승인은 config 또는 환경 변수(예: ULTIMATE_OPENCLAW_REQUIRE_APPROVAL=1)로 “위험 도구는 한 번 확인” 플로우를 두면 된다. 샌드박스(예: 네트워크 차단)는 2차 스코프로 두고, 일단 타임아웃·승인 플래그부터 넣자.

**M (메모리)**  
지식 JSONL·키워드 한계는 1차에서도 말했다. 장기 학습·확장성은 벡터/임베딩이 들어가면 해소되는데, 필수 3가지에는 안 들어가 있으니 우선순위는 “진화 게이트·툴 권한·회귀 테스트” 다음으로 두고, 지식 스키마만 “tags·요약” 유지하면서 나중에 임베딩 컬럼 추가할 수 있게 남겨두자.

**U (UX)**  
온보딩은 1차 결론대로 진행하고, “권한·승인”이 들어가면 사용자에게 “이 도구는 승인이 필요합니다” 같은 메시지가 나오는 흐름을 한 번 설계해 두면 좋겠다.

**L (모델)**  
이번 피드백에는 모델 전략이 없어서 기존 계획 유지. 로컬/추상화는 2차.

**O (OpenClaw)**  
run_openclaw 보안은 T·S 쪽 결론 따르고, 연동 스펙 문서화는 1차와 동일하게 진행.

**D (문서·온보딩)**  
필수 3가지가 정리되면 docs에 “안전성·진화 게이트·권한” 절을 한 페이지 추가하고, README에 “진화는 검증 후 적용·도구는 권한 체계 있음·테스트로 회귀 방지” 한 줄 넣자.

---

**H (헤드)**

## 3차 토론 — UI 테마(검정/초록/파랑/노랑) + 파일 올리기·스스로 읽고 추론

**안건**: (1) 검은 화면에 초록·파랑·노랑 텍스트로 심플·미니멀 디자인. (2) 사용자가 파일을 올리면 에이전트가 스스로 읽고 추론하는 능력.

---

### 팀 반응

**H**  
두 가지 안건이다. UI는 TUI 색상, 파일은 “올리기 → 읽기 → 추론” 흐름. 각자 한 번씩.

**U (UX)**  
검은 배경은 터미널 기본이 많으니, **텍스트만 색 지정**하면 된다. 초록(You/사용자), 파랑(Ultimate/응답), 노랑(제목·구분선)으로 역할 구분. ANSI 코드만 쓰고 장식은 빼서 미니멀하게 가자.

**A**  
파일 “올리기”는 CLI에선 `--file path`, TUI에선 `/file path` 같은 명령으로 경로 지정. 읽기는 기존 allowlist 안에서만. 읽은 내용을 **메시지에 첨부**해 보내면 LLM이 그걸 보고 추론하면 된다. 별도 도구 호출 없이 한 턴에 “파일 내용 + 사용자 질문”이 들어가게 하면 된다.

**S**  
파일 읽기 시 allowlist 그대로 적용. “올린” 파일 내용은 **도구 로그에 넣지 말 것**(이미 redact 원칙). 업로드 가능 크기 상한(예: 200KB) 두는 걸 제안한다.

**T**  
CLI: `ultimate chat -f ./doc.txt "요약해줘"` 파싱해서, path 읽은 뒤 메시지에 `[Attached file: doc.txt]` + 내용 붙이기. TUI: `/file path` 입력 시 다음 메시지까지 “첨부됨” 상태로 두고, 전송 시 해당 파일 내용 포함. 텍스트 파일 우선. 바이너리/PDF는 “지원 안 함” 메시지로 처리.

**M**  
읽은 파일 내용을 그대로 컨텍스트에 넣으면, 긴 파일일 때 토큰을 많이 쓴다. 상한(예: 8K자) 잘라서 넣거나, “압축 요약”은 2차로 두자.

**P**  
시스템 프롬프트에 “사용자가 첨부한 파일 내용이 메시지에 포함되어 있으면, 그 내용을 바탕으로 질문에 답하라” 한 줄 넣으면 역할이 명확해진다.

**E, O, L, D**  
진화·연동·모델·문서는 이번 스코프에서 손대지 않고, 구현 후 INTERFACE-DESIGN에 “테마·파일 첨부”만 보강하자.

---

**H**  
결론만 정리한다.

1. **TUI 테마** — 초록(You·사용자 텍스트), 파랑(Ultimate·응답 텍스트), 노랑(제목·구분선). 배경은 터미널 기본. 미니멀.
2. **파일 첨부** — CLI: `-f path` / `--file path`. TUI: `/file path`로 첨부, 다음 메시지에 내용 포함. allowlist 적용, 텍스트만, 크기 상한(예: 200KB 또는 8K자).
3. **추론** — 첨부 내용을 사용자 메시지에 `[Attached file: ...]` 형태로 붙여 보냄. 시스템 프롬프트에 “첨부 파일 내용을 바탕으로 답하라” 명시.
