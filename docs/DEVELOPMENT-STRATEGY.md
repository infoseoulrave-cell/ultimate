# 어떻게 개발해야 가장 진화된 에이전트가 나올까

**원칙**: “진화된” 에이전트 = **한 번에 완성하는 게 아니라**, **작동하는 최소 루프**를 먼저 만든 뒤, **측정·피드백**으로 레이어를 하나씩 키우는 방식이 가장 잘 나온다.

---

## 1. 진화 전략 요약

| 원칙 | 의미 |
|------|------|
| **최소 루프 먼저** | “입력 → 두뇌 → 페르소나 → 출력” 한 사이클을 가장 얇게 구현한다. 도구는 나중에. |
| **측정을 처음부터** | 첫 버전부터 로그·이벤트를 남겨, 나중에 KPI·피드백 루프를 붙일 수 있게 한다. |
| **레이어 분리** | 제어 / 지능 / 페르소나를 모듈로 나누어, 한쪽만 바꿔도 “진화”가 가능하게 한다. |
| **OpenClaw 활용** | 채널·스킬은 OpenClaw에 맡기고, 우리는 “두뇌·페르소나·일부 전용 스킬”에만 집중한다. |
| **반복** | 한 단계가 돌아가면, 다음에 “도구 1개 추가” 또는 “페르소나 문장 1세트 개선”처럼 작은 단위로 확장한다. |

---

## 2. 진행 단계 (진화 순서)

### Phase 0: 아키텍처 한 줄 정하기 (1일)

- **결정**: “ultimate는 OpenClaw **스킬(또는 Gateway 앞단)** 로 동작한다. 사용자 메시지 → 우리 두뇌·페르소나 → 응답(및 필요 시 openclaw 도구 호출).”
- **산출물**: `docs/ARCHITECTURE.md` 한 페이지 (ultimate ↔ OpenClaw 관계, 진입점, 데이터 흐름).
- **이렇게 하면**: 나머지 단계에서 “우리가 뭘 만드는지”가 흔들리지 않는다.

### Phase 1: 최소 루프 (1~2주)

- **목표**: 도구 없이, “메시지 입력 → LLM(시스템 프롬프트: NEXUS + 따뜻한 페르소나) → 응답 텍스트” 한 번 돌리기.
- **구현**:
  - 진입점: CLI 한 개 명령 (예: `ultimate chat "오늘 할 일 정리해줘"`).
  - 설정: LLM API 키·모델 1개 (환경 변수 또는 `~/.ultimate/config`).
  - 시스템 프롬프트: NEXUS 원칙 + “사용자에게는 따뜻하고 명료하게 답한다” 규칙 3~5줄.
  - 로그: 입력/출력/에러를 파일 또는 stdout에 남긴다 (나중에 평가용).
- **산출물**: 한 번 호출하면 한 번 답이 나오는 실행 가능한 코드.
- **이렇게 하면**: “진화”의 기준선이 생긴다. 이후 도구·페르소나 개선이 “이 루프 위에 붙는 것”으로 정리된다.

### Phase 2: OpenClaw와 연결 (1주 내외)

- **목표**: Phase 1 루프를 OpenClaw이 호출할 수 있게 한다.
- **선택지**:
  - (A) OpenClaw **스킬**로 패키징: OpenClaw 에이전트가 우리 스킬을 “도구”처럼 호출.
  - (B) **Gateway 앞단**: 사용자 메시지가 우리 서비스로 먼저 오고, 우리가 판단 후 OpenClaw agent/도구를 호출.
- **산출물**: OpenClaw에서 한 채널(예: WebChat)로 메시지 보내면, 우리 두뇌·페르소나로 답이 나오는 경로.
- **이렇게 하면**: 기존 플러그인·스킬을 그대로 쓰면서, “말투·판단”만 우리 것으로 교체할 수 있다.

### Phase 3: 도구 1개씩 추가 (지속)

- **목표**: 두뇌가 “할 수 있는 일”을 하나씩 늘린다.
- **순서 예**:  
  1) openclaw CLI 래퍼 (예: “openclaw agent …” 실행·결과 파싱)  
  2) 파일 읽기/쓰기 (허용 디렉터리 내)  
  3) 그다음 필요한 것 1개 (검색, 캘린더, 노트 등).
- **규칙**: 도구마다 **스키마(이름, 인자, 설명)** 를 문서·코드에 남기고, 로그에 “어떤 도구를 썼는지” 기록.
- **이렇게 하면**: “진화”가 “도구 개수”가 아니라 “목적 달성률·사용자 만족”으로 측정할 수 있게 된다.

### Phase 4: 피드백 루프 (NEXUS 평가)

- **목표**: “감정이 아닌 데이터로 판단”을 구현한다.
- **구현**:
  - 최소 KPI: 호출 횟수, 도구 호출 횟수, 에러율, (가능하면) 작업 완료 여부 또는 사용자 피드백 플래그.
  - 로그를 주기적으로 보거나, 간단 대시/요약 스크립트로 “어떤 도구가 자주 쓰이는지, 어디서 실패하는지” 확인.
  - 이 결과를 “다음에 개선할 도구·프롬프트” 결정에 반영.
- **이렇게 하면**: 에이전트가 “기능이 많아지는 것”을 넘어 “실제로 더 잘 동작하도록” 진화한다.

### Phase 5: 페르소나 진화

- **목표**: “따뜻한 톤”을 고정 문구가 아니라, 데이터로 다듬을 수 있게 한다.
- **구현**:
  - 좋았던 응답 예시를 모아서 시스템 프롬프트나 few-shot에 반영.
  - “너무 길다/너무 딱딱하다” 같은 피드백이 있으면, 프롬프트 규칙 1~2줄씩 수정.
  - (선택) 사용자 설정으로 “톤 강도”(차분 ↔ 매우 따뜻) 조절.
- **이렇게 하면**: 같은 로직(NEXUS) 위에서 “말투”만 진화시킬 수 있다.

---

## 3. 진행 순서 다이어그램

```
Phase 0: 아키텍처 한 줄
    ↓
Phase 1: 최소 루프 (입력 → LLM+페르소나 → 출력, 로그)
    ↓
Phase 2: OpenClaw 연동 (스킬 또는 Gateway 앞단)
    ↓
Phase 3: 도구 1개씩 추가 (래퍼 → 파일 → …)  ←──┐
    ↓                                              │
Phase 4: 피드백 루프 (KPI·로그·개선 결정) ──────────┘
    ↓
Phase 5: 페르소나 진화 (프롬프트·예시·설정)
```

Phase 3~5는 **반복**: 도구 추가 → 측정 → 페르소나 조정 → 다시 도구/시나리오 추가.

---

## 4. 하지 말 것 (진화를 막는 것)

- **처음부터 모든 도구·채널 구현**: OpenClaw이 있는 것을 재사용하고, 우리는 두뇌·페르소나·필요한 도구만.
- **측정 없이 기능만 쌓기**: 로그/KPI 없이 확장하면 “어디가 약한지” 모른다.
- **페르소나와 로직 한덩어리**: 분리해 두어야 “말투만 바꾸는 진화”가 가능하다.
- **완벽한 설계 후 구현**: Phase 0만 정하고, Phase 1을 빨리 돌려 본 뒤, 그 다음 단계를 구체화하는 편이 진화에 유리하다.

---

## 5. 첫 주에 할 일 체크리스트

- [ ] Phase 0: `docs/ARCHITECTURE.md`에 ultimate ↔ OpenClaw 관계·진입점 한 페이지 작성.
- [ ] Phase 1: 저장소에 `package.json` + 진입 스크립트 1개. 환경 변수로 LLM API. 시스템 프롬프트 1개. `ultimate chat "..."` 한 번 돌리기.
- [ ] Phase 1: 모든 호출에 대해 입력/출력/에러 로그 남기기 (파일 또는 stdout).

이 순서로 가면, **가장 진화된 에이전트**는 “한 번에 완성한 것”이 아니라 **측정 가능한 최소 루프에서 시작해, 피드백으로 레이어를 키운 것**이 된다.
