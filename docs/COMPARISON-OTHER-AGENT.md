# 다른 에이전트 설계 vs Ultimate 비교

**질문**: “다른 에이전트의 이야기야. 우리와 많이 달라?”

**요약**: **방향은 비슷하고(로컬 에이전트, 도구, 기억), 구조·범위·권한·모델 전략은 꽤 다릅니다.** 우리는 지금 “채팅 + 웹/지식 + OpenClaw 연동”에 가깝고, 그쪽은 “파일/터미널/브라우저 자동화 → 데스크톱 제어”에, **권한·4층 아키텍처·로컬 우선 모델**을 제품 중심으로 둡니다.

---

## 1. 범위 (1차/2차)

| 항목 | 다른 에이전트 | Ultimate (현재) |
|------|----------------|------------------|
| **1차** | 파일 / 터미널 / **브라우저 자동화**만 | 파일(읽기), **웹 URL 조회**, **지식 저장·검색**, OpenClaw(터미널·채널 포함) |
| **2차** | **데스크톱 앱 제어**(클릭·입력·윈도우) | 미정 (문서상 “확장”만) |
| **우리만** | — | **인터넷 돌아다니며 학습**(fetch_url + save/read_knowledge), **NEXUS 페르소나**, OpenClaw 생태계 연동 |
| **그쪽만** | 브라우저 자동화, 이후 데스크톱 제어 | — |

→ **다름**: 1차를 “파일/터미널/브라우저”로 고정하는지 vs “웹/지식/OpenClaw”까지 넣는지. 우리는 브라우저 자동화 없음, 데스크톱 제어 없음. 우리는 “웹+학습”이 있고, 그쪽은 “자동화 범위 고정 후 데스크톱”이 있음.

---

## 2. 아키텍처 (4층 vs 우리)

| 층 | 다른 에이전트 | Ultimate (현재) |
|----|----------------|------------------|
| **UI** | **데스크톱 앱**(Tauri/Electron) | CLI + TUI 채팅 (앱 없음) |
| **Agent Core** | **Plan → Act → Observe** 명시적 루프 | LLM + 도구 루프 (단계 나누기는 프롬프트로만 유도) |
| **Tool Bus** | **명시적 툴 등록**(terminal, fs, browser, app control) | 도구 목록 + runTool (별도 “버스” 레이어 없음) |
| **Memory** | **SQLite + 벡터DB**(작업 이력/선호/프로젝트 컨텍스트) | JSONL 지식 저장소 + 호출 로그 (SQLite·벡터 없음) |

→ **다름**: 그쪽은 **UI / Core / Tool Bus / Memory** 4층으로 나누고, Core는 “계획–실행–관찰” 루프, 메모리는 DB+벡터. 우리는 **플랫한 구조**(entry, brain, tools, log, knowledge)이고, Plan 단계와 Tool Bus가 없고, 메모리는 JSONL만 있음.

---

## 3. 권한 시스템

| 항목 | 다른 에이전트 | Ultimate (현재) |
|------|----------------|------------------|
| **위치** | **제품의 중심** | 부분적 (경로 allowlist, URL 차단만) |
| **위험 명령** | **항상 승인**(rm, 시스템 설정, 외부 전송) | rm·시스템 명령 직접 노출 없음 (openclaw 경유 시 제어는 openclaw 쪽) |
| **경로** | **allowlist**(예: /workspace만 수정) | read_file만 allowDirs, **쓰기 없음** |
| **dry-run / kill switch** | **필수** | 없음 |
| **audit log** | **모든 액션 저장** | 호출·도구 사용·에러 로그만 (액션 단위 audit 아님) |

→ **많이 다름**: 그쪽은 **권한을 중심**에 두고, 승인·allowlist·dry-run·kill switch·audit을 전제. 우리는 **권한이 부가적**이고, 위험 명령 승인·dry-run·kill switch·전액션 audit 없음.

---

## 4. 모델 전략

| 항목 | 다른 에이전트 | Ultimate (현재) |
|------|----------------|------------------|
| **기본** | **로컬 모델**(Ollama/llama.cpp) | 클라우드 1개(OpenAI 호환) |
| **고난도** | **선택적 클라우드 라우팅** | 없음 (단일 API) |
| **교체** | **인터페이스 추상화**로 모델 교체 가능 | 설정으로 URL·모델 키만 변경, 추상화 레이어 없음 |

→ **다름**: 그쪽은 **로컬 우선 + 필요 시 클라우드**이고 모델 추상화. 우리는 **단일 원격 API** 고정.

---

## 5. MVP 순서

| 단계 | 다른 에이전트 | Ultimate (현재) |
|------|----------------|------------------|
| 1 | 채팅 + **터미널 실행** + **파일 읽기/수정** | ✅ 채팅, ✅ 파일 읽기, 터미널은 OpenClaw 경유, **파일 수정 없음** |
| 2 | **작업 계획기**(멀티스텝) + **재시도/롤백** | 프롬프트로 “단계 나누기”만, 재시도/롤백 없음 |
| 3 | **스케줄러**(반복 작업) + **플러그인 SDK** | 없음 |
| 4 | **테스트**(회귀 시나리오) + **패키징**(자동 업데이트) | 없음 |

→ **다름**: 우리는 그쪽 MVP 1단계의 “채팅 + 파일 읽기” 근처에 있고, **파일 쓰기·명시적 계획기·스케줄러·SDK·회귀 테스트·패키징**은 없음.

---

## 6. 같은 점

- **로컬 실행** 에이전트.
- **도구**로 파일·터미널(우리는 openclaw)·웹(우리는 fetch_url) 접근.
- **기억/컨텍스트** 필요 인식 (그쪽: DB+벡터, 우리: JSONL 지식).
- **점진적 확장** (그쪽: 1차→2차, MVP 1→4 / 우리: Phase 0~5).

---

## 7. 정리

| 질문 | 답 |
|------|----|
| **많이 달라?** | **범위·아키텍처·권한·모델·MVP** 다 다름. “로컬 에이전트 + 도구 + 기억”이라는 큰 그림만 비슷. |
| **우리만 있는 것** | 웹 돌아다니며 학습, NEXUS 페르소나, OpenClaw 연동, 따뜻한 톤. |
| **그쪽만 있는 것** | 4층 구조, Plan–Act–Observe, 권한 중심(승인/dry-run/kill switch/audit), 로컬 우선 모델, 브라우저·데스크톱 제어, 스케줄러·플러그인 SDK. |
| **가져오기 좋은 것** | (1) **권한 중심** 설계(allowlist, audit, dry-run, kill switch), (2) **Plan–Act–Observe** 또는 작업 계획기, (3) **메모리**를 SQLite/벡터로 올리는 건 2차 검토. |

원하면 “우리 범위에 맞춘 4층 스케치” 또는 “권한 레이어만 먼저 도입하는 설계”로 이어서 정리할 수 있음.
